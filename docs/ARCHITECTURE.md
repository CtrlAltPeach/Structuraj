# Архитектура

## Разделение слоёв

```
   выбор папки            команды Tauri            SQLite-индекс
        │                       │                        │
  ┌─────▼───────┐        ┌──────▼──────┐          ┌──────▼──────┐
  │  React + TS │◄──────►│   Rust      │◄────────►│ index.sqlite│
  │  только UI  │ invoke │  вся работа │  rusqlite│  временный  │
  └─────────────┘        └──────┬──────┘          └─────────────┘
                                │ читает
                         ┌──────▼──────┐
                         │ *.json      │  только чтение,
                         │ *.jsonl     │  файлы не меняются
                         └─────────────┘
```

Правило, на котором держится всё остальное: **фронтенд не знает о JSON**. Он
получает уже готовые страницы данных и рисует их. Ни один мегабайт исходных
файлов в вебвью не попадает. Поэтому интерфейс не тормозит на двух гигабайтах.

Единственная граница — `src/api.ts` и команды в `src-tauri/src/lib.rs`. Полное
описание в [API.md](API.md).

## Модули Rust

| файл | ответственность |
|---|---|
| `scan.rs` | обход папки, потоковый разбор, канонизация путей, наполнение индекса |
| `db.rs` | схема SQLite, коды типов, битовые маски |
| `tree.rs` | сборка дерева в двух режимах, экспорт в Markdown |
| `query.rs` | страницы значений, список записей, чтение записи, ошибки |
| `model.rs` | типы, уходящие во фронтенд |
| `lib.rs` | команды Tauri, состояние приложения, события прогресса |

## Канонический путь

Основа дедупликации. Индексы массивов схлопываются в `[]`, поэтому одинаковые
ключи из разных файлов и разных элементов массива получают **одну и ту же строку
пути** и попадают в один узел автоматически.

| правило | пример |
|---|---|
| корень | `$` |
| ключ объекта | `$.user` |
| элемент массива | `$[]`, `$.tags[]` |
| вложенность | `$[].items[].sku` |

Корень записи зависит от формата файла:

* `.jsonl` и `.ndjson` — каждая строка это запись, путь записи `$[]`
* `.json` с массивом верхнего уровня — каждый элемент это запись, путь `$[]`
* `.json` с объектом или скаляром — весь файл одна запись, путь `$`

Из-за этого корневой узел `$` может одновременно быть и массивом, и объектом:
в одних файлах верхний уровень массив, в других объект. Это не ошибка, а честное
отражение набора данных.

Ключи с точками и скобками внутри (`{"a.b": 1}`) делают строку пути
неоднозначной. На отображение это не влияет, а всё, что должно быть точным —
восстановление записи, переходы по дереву — работает не через разбор строки, а
через цепочку `parent_id` в таблице `paths`.

## Схема индекса

База пересоздаётся при каждом скане. Она временная и живёт вне папки с данными:
`%LOCALAPPDATA%\com.structuraj.app\index.sqlite`.

```sql
files (id, abs_path, rel_path, kind, bytes, records)

paths (id, path, parent_id, key, depth, is_array, cnt, nonempty, mask)
--  cnt      сколько раз путь встретился
--  nonempty сколько из них с непустым значением
--  mask     битовая маска встреченных типов

vals  (path_id, file_id, rec, vtype, txt, num, trunc)
--  одна строка на каждое скалярное значение и на каждый пустой контейнер
--  txt   текстовое представление: по нему фильтр и сортировка строк
--  num   числовое представление: по нему сортировка чисел
--  trunc 1, если строка длиннее 4096 символов и обрезана

errors (id, file, line, message)
meta   (k, v)   -- сводка скана и корневая папка
```

Коды `vtype`: `0` null, `1` bool, `2` number, `3` string, `4` object, `5` array.
Биты `mask`: `1` null, `2` bool, `4` number, `8` string, `16` object, `32` array.

Настройки на скорость записи, а не на надёжность — база одноразовая:

```sql
PRAGMA journal_mode = MEMORY;
PRAGMA synchronous  = OFF;
PRAGMA temp_store   = MEMORY;
PRAGMA cache_size   = -262144;   -- 256 МБ
```

Индексы по `vals` строятся **после** массовой вставки: так вставка идёт в разы
быстрее, чем с живыми индексами.

## Как идёт скан

1. `walkdir` собирает список файлов по расширениям `.json`, `.jsonl`, `.ndjson`. Каталоги `.git` пропускаются.
2. Для `.json` читается первый непробельный байт. `[` — массив верхнего уровня, тянем поэлементно через `deserialize_seq`, весь файл в память не грузим. Иначе читаем поток значений: это покрывает и одиночный объект, и несколько значений подряд.
3. Для `.jsonl` читаем построчно, BOM снимаем, пустые строки пропускаем.
4. Каждая запись обходится рекурсивно. Пути интернируются в `HashMap<String, i64>`, счётчики копятся в памяти, в базу пишутся значения.
5. Транзакция коммитится каждые 250 000 значений — чтобы не раздувать страницы в кеше.
6. В конце одним проходом пишутся `paths`, строятся индексы, сохраняется сводка.

Битый файл не роняет скан: ошибка ложится в `errors` и обход идёт дальше.
С одного файла в отчёт попадает не больше 100 ошибок — иначе испорченный гигабайт
забил бы вкладку миллионом одинаковых строк.

Прогресс уходит во фронтенд событием `scan:progress` не чаще 20 раз в секунду.

## Сборка дерева

### Схлопывание `[]`

Узел элемента массива убирается, если у него есть дети и **нет** скалярных типов.
Тогда ключи объектов висят прямо под массивом:

```
items   массив
  sku
  qty
```

Если массив скалярный, узел `[]` остаётся — иначе значениям негде жить:

```
tags    массив
  []    string
```

Смешанный массив (и скаляры, и объекты) тоже сохраняет узел `[]`.

### Режим `byPath`

Прямая иерархия по `parent_id`. `user.name` и `order.name` — разные узлы,
у каждого свой счётчик и свои значения.

### Режим `byName`

Узел это **имя ключа**. Все одноимённые пути сливаются в один узел, счётчики
складываются, список путей едет в поле `paths`.

Куда подвесить такой узел, решает голосование: родителем становится тот, под
которым ключ встречается чаще (вес — счётчик вхождений). Побочный эффект виден
сразу: если `name` чаще лежит в корне, чем в `user`, то из `user` он уедет наверх,
и под `user` останется только `age`. Это цена слияния, а не баг.

Циклы (`a` внутри `b` и `b` внутри `a`) рвутся: такой ключ переезжает в корень.

Элементы скалярных массивов получают имя вида `tags[]`, иначе все `[]` проекта
слиплись бы в один узел.

### Пустые ключи

`nonempty` считается на этапе скана, для каждого пути отдельно:

| значение | непустое? |
|---|---|
| `null` | нет |
| `""` и строка из пробелов | нет |
| `[]`, `{}` | нет |
| `false`, `0` | **да** — это значения, а не пустота |
| любая другая строка или число | да |

В дереве узел получает `nonEmpty` = своё значение плюс сумма по всему поддереву.
Поэтому объект, внутри которого одни `null`, считается пустым целиком, а
переключатель «скрыть пустые» срезает ветку одним условием `nonEmpty === 0`.

## Чтение одной записи

Запись **не собирается из индекса** — она перечитывается из исходного файла по
паре `(file_id, rec)` с досрочным выходом, как только нужный элемент найден.

Так решаются сразу три проблемы: длинные строки не обрезаны, порядок элементов
массива не угадывается, а пустые контейнеры не теряются. Цена — линейный проход
по файлу до нужной записи, что при клике незаметно.

## Пределы и настройки

| параметр | значение | где |
|---|---|---|
| обрезка строкового значения | 4096 символов | `db.rs: MAX_TEXT` |
| ошибок с одного файла | 100 | `scan.rs: MAX_ERRORS_PER_FILE` |
| коммит транзакции | каждые 250 000 значений | `scan.rs` |
| строк на странице значений | 200 | `ValuesTab.tsx: PAGE` |
| потолок `limit` в запросе | 5000 | `query.rs` |
| строк во вкладке ошибок | 5000 | `query.rs` |
| частота событий прогресса | ≤ 20/с | `lib.rs` |

Расчётный объём — 100 МБ … 2 ГБ исходных данных. Размер индекса сопоставим с
размером исходников: на каждое скалярное значение приходится одна строка в `vals`.
Замеров на наборах такого масштаба пока не делалось — цифры выше это проектные
ограничения, а не результаты бенчмарков.

## Сборка

Если проект лежит в синхронизируемой папке, каталог сборки стоит вынести наружу:
скопируй `src-tauri/.cargo/config.toml.example` в `config.toml` и пропиши свой путь.
Без этого облако пытается синхронизировать десятки гигабайт объектных файлов.
Сам `config.toml` в репозиторий не попадает — путь у каждого свой.
